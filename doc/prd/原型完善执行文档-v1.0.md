## 0. 文档目的

本文不是技术实现方案，而是一期产品、原型和验收的执行基线。目标是把已经确定的产品痛点和产品区分，转成可以直接实现、演示和验收的页面、状态、数据和交互。

完成本文定义的原型后，用户应该能在一次演示中走通：

```text
进入工作台
  -> 导入或补充 3—6 套候选房源
  -> 确认 AI 提取的房源字段
  -> 设置预算、通勤和居住偏好
  -> 获得有依据的房源推荐
  -> 查看目标房源详情和待确认事项
  -> 上传合同并核对房源承诺
  -> 继续追问租房常识并得到下一步行动
```

当前原型已完成一期基线确认，后续进入工程设计与正式开发。原型中的演示数据可以是固定种子数据，但用户输入、筛选条件和上下文必须真实影响页面结果，不能使用与输入无关的固定报告。任何超出本文范围的需求，必须先更新需求和验收标准，再进入开发。

### 0.1 一期基线使用规则

- 当前原型负责确认页面结构、核心流程、交互状态和演示口径；工程实现以可测试、可维护的组件和服务重建，不要求复用原型代码。
- 本文负责确认一期范围、数据边界、产品承诺、关键状态和验收场景；实现结果必须能回放本文第 10、11 节定义的场景和清单。
- “本次工作台临时数据”“用户导入或补充房源”“信息完整度与待核实项”“不承诺房源真实有效”是一期不可弱化的产品边界。
- 任何新增能力、范围扩大或产品承诺，必须先记录在本文或对应 PRD 中，并同步更新原型和验收用例。

## 1. 已确认的产品定义

### 1.1 产品定位

RentGraph 是一个**以房源推荐为主、合同审查和租房常识为辅的租客决策工作台**。产品不建立长期房源库，用户可以在当前工作台中粘贴、手动填写或批量导入自己找到的候选房源；Agent 将这些临时数据整理成可比较的结构化信息。

对话是主要交互方式，但产品价值不是泛聊天，而是帮助用户完成从选房到签约的连续决策。当前会话需要暂存候选房源、目标房源、合同和字段确认结果，以维持上下文；这些数据只承诺“本次工作台使用”，不承诺长期保存或跨工作台同步。

### 1.2 三项能力的关系

| 能力 | 产品角色 | 主要结果 |
|------|----------|----------|
| 房源推荐 | 主场景 | 导入候选、确认字段、设置偏好、比较候选、解释推荐理由 |
| 合同审查 | 关键差异化能力 | 核对房源承诺与合同条款，发现风险并给出谈判建议 |
| 租房常识 | 上下文辅助能力 | 结合城市、租住阶段、房源和合同回答问题并给出行动建议 |

### 1.3 产品边界

- 一期不做新的房源信息平台，不承诺覆盖所有外部平台房源。
- 一期不建立自己的长期房源库，基础数据来自用户粘贴、手动填写、批量粘贴、Excel、Word、可解析文本文件或外部链接。
- 当前会话可以暂存临时候选房源和合同，用于后续比较、绑定和问答；关闭或新建工作台后的长期保存策略暂不承诺。
- 推荐必须能解释依据、限制条件和不确定性，不输出无依据的单一排名。
- 合同审查输出风险和建议，不输出确定性的法律结论。
- 租房常识必须区分常识、经验和法规政策；涉及法律政策时提供来源或提示核实。
- 不承诺房源真实有效，不把更新时间、库存数量或“已验证”作为产品能力；只展示数据来源、信息完整度和待核实项。

## 2. 用户痛点到原型任务

| 用户痛点 | 原型必须提供的解决方式 | 验收表现 |
|----------|------------------------|----------|
| 房源太多，无法按个人条件筛选 | 本次候选房源导入、硬约束、软偏好、筛选和比较 | 导入 3—10 套后，修改预算或通勤，候选结果和推荐理由发生变化 |
| 只看月租，忽略真实成本 | 房源卡片展示租金、押金、物业、网费、中介费和通勤成本 | 推荐结果显示月度总成本及缺失费用 |
| 房源信息不完整或真假难判断 | 数据来源、信息完整度、字段缺失和待核实项 | 不输出“真实有效”结论，缺失字段和待核实事项明显可见 |
| 房东承诺和合同条款相互脱节 | 房源详情与合同审查建立同一房源上下文 | 能看到“房源承诺 / 合同原文 / 核验结果”的对应关系 |
| 合同看不懂、不会谈 | 条款解释、风险报告、原文定位、谈判话术 | 点击风险可以回到对应条款，并得到下一步建议 |
| 租房知识分散且不适用于当前情况 | 上下文问答 | 问题回答引用当前房源、城市、阶段或合同来源 |
| 看房和退租证据难以回溯 | 备注、待确认项、行动记录 | 用户可以查看某套房的来源、看房记录和合同关联 |

## 3. 产品区分必须在原型中出现

产品区分不能只写在介绍文案里，必须被用户在交互中看见。

### 3.1 用户导入的临时候选数据

房源不是一张只有“标题 + 月租”的卡片，也不是产品库存条目。每套临时候选房源都必须展示或能查看：

- 数据来源：用户粘贴、用户手动填写、用户批量导入文件或外部链接
- 本次导入批次与原始内容片段
- 信息完整度，以及缺失字段和待核实项
- 租金、押金、付款方式及一次性费用
- 物业费、网费、停车费、维修费等长期费用
- 区域、通勤时间、面积、户型、楼层、朝向和配套
- 可入住时间、宠物、转租、合租和独立卫浴等关键条件
- 用户备注、看房记录和待确认问题

一期支持以下输入方式：

- 粘贴单条房源描述
- 手动填写单条房源信息
- 批量粘贴多条房源信息
- 上传 Excel（`.xlsx` / `.xls`）
- 上传 Word（`.docx` / `.doc`）
- 上传可解析的文本文件（如 `.txt` / `.csv` / `.md`）

所有非结构化输入都必须先经过“AI 提取字段 → 用户确认 / 修改 → 加入本次候选房源”流程，不能直接把未经确认的字段用于推荐。

### 3.2 可解释推荐

推荐卡片必须同时回答五个问题：

1. 为什么推荐这套？
2. 哪些硬条件满足或不满足？
3. 它的真实成本和主要风险是什么？
4. 这些信息来自哪里，完整度如何？
5. 用户下一步还需要确认什么？

不能只显示“推荐指数 92”或“第一名”。推荐结果至少包含“推荐理由、取舍、风险、待确认、下一步”五个区域。

### 3.3 房源与合同核验

这是第一版最重要的差异化交互。用户从本次候选房源中选定目标房源后绑定合同，原型展示“房源承诺 / 合同条款 / 待确认事项”核验表：

| 房源信息 / 承诺 | 合同对应条款 | 结果 | 建议 |
|----------------|--------------|------|------|
| 月租 5,800 元 | 第 4 条：月租 6,000 元 | 冲突 | 与房东确认并要求修改 |
| 押一付一 | 第 5 条：押二付一 | 冲突 | 计算新增资金占用 |
| 允许养猫 | 未找到对应条款 | 未约定 | 写入补充协议 |
| 物业费由房东承担 | 第 9 条：乙方承担 | 冲突 | 标记为高优先级确认项 |

核验结果必须能回到房源字段和合同原文，不能只展示一个抽象分数。未在合同中找到对应约定时，结果应为“未约定 / 待确认”，而不是推断为合同已经承诺。

### 3.4 上下文租房常识

用户问“物业费谁承担”“提前退租怎么办”时，Agent 应优先使用当前房源和合同上下文；没有对应材料时，明确说明回答属于通用建议，并询问城市和租住阶段。

## 4. 原型信息架构

产品仍以对话工作台为主，不拆成互相割裂的后台系统。建议页面层级如下：

```text
租房决策工作台
  ├─ 当前对话
  │   ├─ 房源推荐卡
  │   ├─ 房源详情卡 / 抽屉
  │   ├─ 合同核验卡
  │   └─ 租房常识回答
  ├─ 本次候选房源
  │   ├─ 添加房源
  │   ├─ 批量导入
  │   ├─ 字段确认
  │   └─ 候选详情、目标房源与关联合同
  ├─ 本次合同
  └─ 最近对话
```

### 4.1 首页默认状态

首页不再把三项能力设计成完全等权的三个入口。主入口应是“从本次候选房源开始”：

- 主标题：从选房到签约，帮你做出更可靠的租房决定。
- 主输入：告诉我你的预算、通勤和居住要求，或直接粘贴 / 导入候选房源。
- 主操作：添加房源 / 批量导入 / 开始筛选。
- 次操作：手动填写、审查已绑定合同、问租房常识。
- 页面可以显示“本次已导入 X 套”，但不得展示房源库数量、产品库存、房源更新时间等长期运营指标。
- 页面必须明确提示“候选房源和合同仅用于本次工作台”，不出现“我的房源”“已验证房源”“仅自己可见”等未实现承诺。

### 4.2 对话与结构化视图的关系

- 对话负责收集需求、解释结果和承接追问。
- 房源卡负责展示字段、比较结果和推荐依据。
- 房源详情抽屉负责查看完整信息、证据和备注。
- 合同核验卡负责展示房源与合同的逐项对应关系。
- 所有卡片都必须带稳定的房源 ID 或合同 ID，不能静默切换对象。

## 5. 需要完善的原型流程

### 流程 A：房源导入与推荐主流程（P0）

| 步骤 | 用户操作 | 原型响应 |
|------|----------|----------|
| A1 | 进入工作台 | 展示空态和“添加房源 / 批量导入”主入口 |
| A2 | 粘贴、手动填写或上传房源 | 展示导入来源、解析进度和候选条数；比较范围为 3—10 套 |
| A3 | 查看 AI 提取结果 | 逐套确认或修改租金、押金、物业费、通勤、户型等字段 |
| A4 | 确认硬约束与软偏好 | 明确哪些条件会淘汰房源，哪些只影响排序 |
| A5 | 查看推荐结果 | 展示推荐房源、匹配理由、取舍、真实成本、信息完整度和待核实项 |
| A6 | 打开某套房源 | 展示来源、原始内容、结构化字段、待确认事项和备注 |
| A7 | 选定目标房源并追问 | 对话绑定当前房源，回答不得引用其他候选房源 |

### 流程 B：房源与合同核验（P0）

| 步骤 | 用户操作 | 原型响应 |
|------|----------|----------|
| B1 | 在目标房源详情中点击“绑定合同” | 新建绑定当前房源的合同审查任务，并显示房源标签 |
| B2 | 上传 PDF 或粘贴合同 | 显示上传 / 解析 / 抽取 / 核验状态 |
| B3 | 查看核验结果 | 逐项展示“房源承诺 / 合同条款 / 待确认事项”及一致、冲突、未约定和无法判断 |
| B4 | 点击核验项 | 同时定位房源字段来源和合同原文条款 |
| B5 | 查看风险建议 | 展示修改建议、谈判话术和下一步行动 |
| B6 | 继续提问 | 对话同时保留当前房源和当前合同上下文 |

### 流程 C：租房常识问答（P0）

| 场景 | 必须表现 |
|------|----------|
| 有当前房源、无合同 | 结合房源字段回答，并标注仍需确认的合同内容 |
| 有当前房源和合同 | 优先引用合同条款，再补充通用知识 |
| 无当前上下文 | 先回答通用原则，再询问城市和租住阶段 |
| 涉及法规政策 | 展示来源、适用范围和核实提示 |
| 用户问题超出能力 | 明确无法判断的原因，不生成确定性结论 |

## 6. 原型页面与状态清单

以下状态必须在原型中至少出现一次。状态可以作为同一页面的交互变体，不要求拆成独立 HTML 页面。

| 模块 | 必须制作的状态 |
|------|----------------|
| 工作台 | 首次空态、已有临时候选、无候选、加载中、服务异常 |
| 候选房源 | 列表、搜索、筛选、排序、信息不完整、空列表、添加、批量导入 |
| 房源录入 | 手动填写、批量粘贴、Excel / Word / 文本文件解析、字段确认、字段缺失、重复提示、加入成功、加入失败 |
| 房源详情 | 完整信息、来源证据、信息完整度、用户备注、待确认项、目标房源、关联合同 |
| 偏好设置 | 硬约束、软偏好、无效输入、修改条件后重新推荐 |
| 推荐结果 | 推荐中、推荐完成、无匹配、部分信息缺失、推荐依据展开、比较模式 |
| 合同核验 | 上传中、解析中、核验中、完成、失败、无匹配条款、冲突条款定位 |
| 租房问答 | 流式输出、停止输出、回答失败、重新生成、来源展开、继续追问 |
| 上下文 | 当前房源标签、当前合同标签、移除标签、切换对象、上下文为空 |
| 历史记录 | 打开、重命名、删除确认、临时数据清理提示、持久化未承诺、旧任务取消 |

## 7. 房源数据最小模型

原型不需要实现数据库，但卡片和详情页必须按以下字段设计，避免后续重新改页面结构。数据属于当前工作台临时上下文，不默认形成长期房源库。

| 字段组 | 最小字段 |
|--------|----------|
| 身份 | `house_id`、标题、区域、详细地址、来源 |
| 数据状态 | 信息完整度、缺失字段、待核实项、可入住时间（如有） |
| 价格 | 月租、押金、付款方式、中介费、物业费、网费、其他费用 |
| 居住 | 面积、户型、楼层、朝向、独立卫浴、采光、家具家电 |
| 位置 | 通勤时间、通勤方式、最近地铁、周边配套 |
| 约束 | 宠物、合租、转租、入住人数、租期要求 |
| 证据 | 原始描述、图片或链接、房东 / 中介承诺、导入来源、导入批次 |
| 用户信息 | 收藏状态、用户备注、看房记录、待确认事项、放弃原因 |
| 关联 | 当前工作台 ID、当前对话 ID、关联合同 ID、导入批次 ID、推荐批次 ID |

### 7.1.1 一期导入与确认约束

- 单条粘贴和手动填写都必须标记来源类型。
- 批量粘贴和文件导入必须展示识别出的房源条数，用户确认后才能加入候选列表。
- 每套房源至少让用户确认：租金、押金 / 付款方式、物业费、通勤、户型；无法提取的字段显示“待确认”。
- 比较操作支持 3—10 套候选房源；少于 3 套时提示继续添加，超过 10 套时要求拆分或移除。
- 外部链接只记录为数据来源，不表示平台实时同步，也不表示房源真实有效。

### 7.1 偏好模型

偏好必须分为两类：

- 硬约束：超出预算、通勤超过上限、区域不接受、必须独立卫浴等，默认淘汰或明确标记不满足。
- 软偏好：南向、采光、楼层、面积、付款方式等，用于排序并说明取舍。

原型必须让用户看懂自己设置的是硬约束还是软偏好，不能把所有条件混成一个神秘分数。

## 8. 推荐结果卡片规格

每套推荐房源至少包含：

- 推荐状态：优先考虑 / 可作为备选 / 不建议
- 推荐理由：满足的关键条件
- 不足与取舍：没有满足的偏好或潜在代价
- 真实成本：月租 + 固定费用 + 一次性费用提示
- 信息风险：缺失、模糊或未经核实的字段
- 待确认问题：看房或联系房东时要问的问题
- 下一步操作：查看详情、加入候选、上传合同、标记放弃

推荐结果顶部应同时提供“按预算 / 按通勤 / 按综合匹配”三种视角，避免产品强行给出唯一答案。每套卡片必须显示数据来源、信息完整度和待核实项；不能用“平台认证”“真实有效”等标签替代证据。

## 9. 原型交互规则

### 9.1 上下文绑定

- 每次对话只能有一个当前主房源，可附加一个当前合同；候选列表可以同时存在 3—10 套房源。
- 房源、合同、附件和消息都必须显示来源标签。
- 打开另一套房源时，必须明确提示“切换当前房源”，不能静默替换。
- 移除上下文标签后，后续回答不得继续使用被移除对象。

### 9.2 流式输出与任务隔离

- 停止输出后保留已生成内容，并展示“重新生成”或“继续追问”明确按钮。
- 新建会话、切换会话、切换房源时，必须取消旧任务。
- 旧任务完成后不能向新会话或新房源追加结果。
- 失败状态必须包含失败原因和可执行的重试动作。

### 9.3 输入能力

- 房源导入入口展示并支持：粘贴、手动填写、批量粘贴、Excel、Word 和可解析文本文件；合同入口单独展示实际支持的格式。
- PDF 上传必须有选择、上传、解析、核验、完成和失败状态。
- 房源文本、Excel、Word 或批量粘贴解析后先展示字段确认，不应直接生成不可修改的推荐结论。
- 图片和 OCR 如果暂不支持，应明确标注为规划能力，不提供误导性的成功状态。

### 9.4 数据真实性

- 自定义预算、通勤、房源文本和用户确认后的房源字段必须改变结果。
- 每份报告必须绑定实际的房源 ID 或合同 ID。
- 演示种子数据可以固定，但不能把固定数据伪装成用户输入后的分析结果。
- 评分和风险等级必须有解释，不只显示数字；房源不使用“真实有效”或产品库存类指标。

## 10. 原型演示数据与验收场景

### 场景 1：推荐结果会随偏好变化

演示时由用户导入 3—6 套房源，覆盖低租金长通勤、较贵但通勤短、合租、独立卫浴和信息缺失等差异。可以包含外部链接来源，但不演示“已失效”或“真实有效”结论。

验收：

- 输入“预算 6,000、通勤 45 分钟、必须独立卫浴”后，推荐结果有明确排序和解释。
- 将预算改为 5,000 或通勤改为 30 分钟后，结果发生变化。
- 选择“允许合租”后，合租房源才进入可推荐集合。
- 推荐卡片分别显示用户粘贴、用户手动填写或外部链接等数据来源，并展示信息完整度和待核实项。

### 场景 2：房源承诺与合同冲突

用户导入的一套目标房源预先确认“押一付一、允许养猫、物业费由房东承担”。绑定合同写成“押二付一、禁止养宠物、物业费由乙方承担”。

验收：

- 核验卡展示“房源承诺 / 合同条款 / 待确认事项”，其中至少有 3 个冲突项。
- 每个冲突项可分别定位房源字段和合同条款。
- 输出修改建议和谈判话术，不直接给出“合同无效”等法律结论。

### 场景 3：上下文租房常识

在同一套房源和合同上下文中连续提问“物业费谁承担”“提前退租要付什么”。

验收：

- 回答优先引用当前合同和房源信息。
- 引用不存在的条款时必须降级为通用建议并说明原因。
- 移除合同上下文后，回答不再声称“根据你的合同”。

## 11. 原型验收清单

- [ ] 首页第一主任务是房源推荐，不是合同审查。
- [ ] 用户能通过粘贴、手动填写、批量粘贴或 Excel / Word / 文本文件导入候选房源。
- [ ] 导入后先展示 AI 提取字段，用户能确认或修改租金、押金、物业费、通勤和户型。
- [ ] 用户能查看、搜索、筛选和打开本次候选房源详情。
- [ ] 房源详情展示数据来源、信息完整度和待核实事项，不承诺真实有效。
- [ ] 比较范围明确限制为 3—10 套候选房源。
- [ ] 用户能设置硬约束和软偏好。
- [ ] 推荐结果包含理由、取舍、真实成本、风险和下一步。
- [ ] 修改预算、通勤或偏好后，结果真实变化。
- [ ] 推荐结果能打开对应房源详情，不会串到其他房源。
- [ ] 选定房源后可以进入绑定的合同核验流程。
- [ ] 房源承诺和合同条款可以逐项对照。
- [ ] 合同风险可以定位原文，并能回到房源字段。
- [ ] 租房常识问答能使用当前房源和合同上下文。
- [ ] 流式输出、停止、重试、切换会话不会产生串线。
- [ ] 上传失败、解析失败、信息缺失和无匹配结果都有明确状态。
- [ ] 页面没有未实现的文件格式、隐私和分享承诺。
- [ ] 三个演示场景可以从头到尾独立重放。

## 12. 本轮明确不做

- 建立产品自有的长期房源库、房源库存运营指标和全网房源覆盖。
- 外部房源平台实时抓取、实时同步和房源真实性保证。
- 地图路线、实时通勤计算和价格趋势预测。
- 图片 OCR、扫描件自动识别和复杂表格自动导入。
- 自动代替律师作出法律结论或保证纠纷结果。
- 独立知识图谱可视化页面。
- 复杂账号套餐、付费、分享权限和多人协作。
- 在没有真实权限体系前承诺合同数据“仅自己可见”。

## 13. 执行顺序

1. 重做工作台空态和“本次候选房源”入口，突出房源推荐主场景和临时数据边界。
2. 制作添加房源流程：粘贴、手动填写、批量粘贴、Excel、Word、文本文件。
3. 制作 AI 字段提取与用户确认流程，覆盖缺失字段、重复提示和导入失败。
4. 制作 3—10 套候选房源列表、详情、偏好设置和可解释推荐结果，完成场景 1。
5. 制作目标房源选择，以及“房源承诺 / 合同条款 / 待确认事项”绑定核验流程，完成场景 2。
6. 将租房常识问答接入当前房源和合同上下文，完成场景 3。
7. 补齐流式输出、停止、重试、切换、附件和失败状态。
8. 用验收清单逐项回放，删除所有与真实行为不一致的库存、真实性、长期保存和格式承诺。
9. 原型验收通过后，再拆分前端组件、数据模型和后端 API。

## 14. 完成定义

满足以下条件，才进入工程设计：

- 三个核心场景可以在同一对话工作台中连续演示。
- 房源推荐是首页主线，合同审查和租房常识围绕目标房源工作。
- 用户可以导入 3—6 套房源，完成字段确认、比较和目标房源选择；产品不需要预置长期房源库。
- 推荐依据、房源来源、合同引用和待确认事项可追溯。
- 自定义输入会改变结果，且不存在固定报告冒充真实分析的情况。
- 所有关键状态都有页面表现：加载、成功、失败、取消、重试、空态和无匹配。
- 当前工作台中的临时候选房源、目标房源、合同、附件和会话之间的绑定关系已经在原型中确认，长期保存策略明确标记为未承诺。
- 产品标题、定位、痛点、差异化和范围与功能地图、PRD保持一致。
