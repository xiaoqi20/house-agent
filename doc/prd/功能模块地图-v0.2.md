# RentGraph 功能模块地图 v0.2

> 项目标题：**从选房到签约，帮你做出更可靠的租房决定。**
>
> 状态：讨论草案，暂不作为代码实现依据
>
> 本文以根目录原型 `租房知识图谱-Agent-Frontend-Protype.html` 和 `租房知识图谱-Agent-登录页-Protype.html` 为主要输入，结合现有 PRD、一期方案和最新补充整理。当前已确认产品主题为租房决策，主场景为房源推荐，合同审查与租房常识作为配套能力。

## 1. 产品主线

RentGraph 是一个**以房源推荐为主、合同审查和租房常识为辅的租客决策工作台**。用户可以维护自己的候选房源，在预算、通勤和居住偏好下做比较和筛选；确定目标房源后，再把合同放进同一条上下文中审查，并随时追问租房常识。对话是主要交互形态，但产品价值不止是聊天，而是帮助用户完成从选房到签约的连续决策。

通用 Agent 主线：

```text
进入产品
  -> 新建或打开对话
  -> 用户输入问题、上下文或附件
  -> Agent 读取当前上下文并流式输出
  -> 用户可以暂停输出、继续追问或补充材料
  -> 对话沉淀为可回看的聊天记录
```

租房领域的三条候选场景主线：

```text
维护房源数据 -> 设置预算、通勤和偏好 -> 筛选、比较、解释推荐理由
确定目标房源 -> 上传/粘贴合同 -> 核对房源承诺、解释条款、发现风险、生成谈判建议
租房知识不了解 -> 结合城市、租住阶段和当前房源提问 -> 给出可执行建议和下一步
```

产品形态以“对话工作台”为主：对话是唯一主入口，分析进度、风险报告、房源比较和引用结果都以消息流中的卡片或可展开面板呈现。合同原文、附件详情、结构化房源信息属于对话上下文的延伸视图，不应发展成互相割裂的多个后台页面。

## 1.1 产品主题与主场景（已确认）

**对外标题**：从选房到签约，帮你做出更可靠的租房决定。

**产品定位**：面向租客的租房决策 Agent。产品侧维护房源数据，并允许用户补充、收藏、备注和修正自己的候选房源；Agent 根据结构化房源信息和用户偏好进行推荐，再把目标房源与合同审查连接起来。

**主场景**：租房推荐。首页和第一阶段验收应优先把用户带到“维护房源 → 比较筛选 → 选出候选”的链路。

**配套能力**：

- 合同审查：核对房源信息和合同约定，解释条款、发现风险、提供谈判建议。
- 租房常识：解释费用、流程、权利和纠纷处理，并结合当前城市、租住阶段和房源上下文回答。

合同风险雷达仍然是一期最适合先做深的技术闭环，但不再代表产品全部定位。

## 1.2 用户痛点

用户真正需要解决的不是“再问一个租房问题”，而是把分散的信息变成可以执行的租房决定：

- 收藏或收到很多房源，却无法按预算、通勤、面积、采光、独立卫浴等条件快速筛选。
- 只看月租，忽略押金、中介费、物业费、网费、维修费和通勤成本，难以比较真实成本。
- 房源描述、聊天承诺、看房记录和合同彼此分离，无法确认“说过的内容”是否真正写进合同。
- 合同条款难以理解，不知道哪些条款会影响提前退租、押金退还、维修责任和续租。
- 租房常识分散在搜索结果和平台文章中，无法结合当前城市、租住阶段和具体房源给出下一步行动。
- 看房、签约、付款和退租证据没有连续记录，出现纠纷时难以回溯。

## 1.3 产品区分与核心价值

RentGraph 不定位为新的房源信息平台，也不把“会聊天”作为主要差异化。产品区分来自**自维护房源数据 + 可解释推荐 + 房源与合同核验 + 连续租房上下文**：

1. **房源池由产品维护，结果围绕租客决策组织**：重点不是房源数量，而是来源、更新时间、有效状态、费用和待确认信息是否完整可靠。
2. **推荐有依据，不只给排名**：每个推荐结果都要说明满足了哪些条件、违反了哪些硬约束、真实成本如何、风险是什么，以及看房前还需要确认什么。
3. **房源承诺可以被合同核验**：把房源卡片中的租金、押金、费用、配置、宠物和转租等信息，与合同条款逐项比对，识别遗漏、冲突和模糊表述。
4. **租房常识服务于当前决定**：回答要关联当前房源、合同、城市和租住阶段，而不是输出脱离场景的百科内容。
5. **结论可追溯**：推荐来自哪些房源字段，风险来自哪条合同原文，待确认事项来自哪里，都应该能回到原始信息查看。

产品核心闭环：

```text
房源数据 -> 偏好与硬约束 -> 可解释推荐 -> 目标房源
  -> 房源承诺与合同核验 -> 风险与谈判建议 -> 看房 / 签约 / 退租行动记录
```

一期不承诺实时覆盖所有平台房源、保证房源真实有效或替用户做法律结论。产品应明确：推荐依赖房源数据的新鲜度和完整度，法律与政策判断需要标注来源及核实边界。

## 2. 功能模块总览

### 核心底座：Agent 对话能力

这是所有租房能力共同依赖的基础模块，优先级高于合同风险、房源建议等具体能力。

- 新建对话、打开已有对话、切换当前对话
- 当前对话上下文：用户消息、Agent 消息、系统提示、附件、结构化结果
- 多轮上下文拼接与长度控制
- 聊天记录：消息顺序、时间、发送状态、失败状态
- Agent 流式输出：逐字或逐段显示、完成、失败、重试
- 暂停输出：用户主动停止当前生成，并保留已经输出的内容
- 停止后的继续方式：继续追问、继续生成或重新生成（交互语义待定）
- 附件上传：选择、上传进度、预览、移除、上传失败
- 附件是否自动进入当前上下文，以及是否需要用户确认
- 消息操作：复制、重新生成、引用、反馈
- 输入框状态：空、输入中、发送中、不可发送、上传中、生成中
- 上下文来源标记：当前对话、附件、合同条款、房源列表、知识库
- 服务中断、网络重连、超时和降级提示

### 租房领域能力 1：租房知识问答

面向“遇到租房知识不了解”的开放式问题，回答应尽量生活化、可执行，并清楚区分常识、经验和需要核实的法律事实。

- 租房流程：看房、签约、入住、续租、退租
- 租金、押金、中介费、物业费、网费、维修费等费用解释
- 常见权益与责任说明
- 押金不退、房东违约、提前退租、维修纠纷等问题引导
- 根据用户所在城市、租住阶段和合同情况补充上下文
- 需要用户补充信息时，提出结构化追问
- 引用法规、政策或合同原文时提供来源
- 对不确定或地区差异明显的答案进行风险提示
- 将知识问答结果沉淀到当前对话，支持继续追问

### A. 账号与进入产品

原型中已经出现登录页，因此账号系统应作为产品级模块单独定义，而不是把登录当作一个跳转按钮。

- 手机验证码登录 / 注册
- 手机号或邮箱密码登录
- 验证码发送、倒计时、重发、频控与错误提示
- 密码显示切换、忘记密码、重置密码
- 微信 / 支付宝 / Apple 等第三方登录（是否一期支持待定）
- 用户协议、隐私政策、勾选校验
- 登录态保持、退出登录、过期重新登录
- 用户资料与当前套餐展示
- 用户数据隔离与合同归属

### B. 工作台与会话

这是原型的主容器，负责承载空态、对话态和分析结果，不承担复杂业务判断。

- 空态欢迎页：用户称呼、产品能力说明、免责说明
- 新建分析：清空当前会话与当前合同上下文
- 当前会话标题与状态
- 消息流：用户消息、Agent 回复、输入中状态、失败状态
- 底部输入框：发送问题、粘贴合同文本、上传文件
- 快捷入口：审查最近合同、违约金怎么谈、押金不退怎么办
- 最近对话列表：打开、重命名、删除、空态
- 会话是否持久化、是否跨设备同步

### C. 合同导入与输入校验

这是主链路的第一步，输入方式和失败反馈必须先定义清楚。

- 粘贴合同全文
- 上传 PDF
- Word 文档上传（原型已承诺，是否纳入一期待确认）
- 图片 / 扫描件入口（原型有图片按钮，但当前方案明确 OCR 延后）
- 文件大小、格式、空文件、超长文本校验
- 文本长度门槛与“这段内容是问题还是新合同”的路由判断
- 重复合同提示
- 上传中、上传成功、提取失败、格式不支持、服务不可用提示
- 失败后引导用户粘贴文本，不生成假报告
- 合同文件名、来源类型、创建时间和原文存储

### 租房领域能力 2：合同理解与风险分析

这是当前原型最完整、现有后端已经投入最多的方向，但需要重新放回“租房 Agent”的整体上下文里。

- 合同全文解释与条款问答
- 条款抽取：条号、类型、原文、金额、日期、当事人
- 关键条款摘要：租期、租金、押金、违约、维修、续租、解约、转租
- 风险雷达：高 / 中 / 低风险、原因、规则依据
- 风险条款原文定位与高亮
- 修改建议与谈判话术
- 合同整体摘要与待确认事项
- 追问“这条是什么意思”“这条对我有什么影响”“怎么和房东谈”
- 合同分析完成后继续在同一上下文中对话
- 没有合同或合同尚未完成分析时，给出明确引导而不是编造结论

### D. 合同分析任务

负责把导入内容转成结构化结果，并把过程状态反馈给用户。

- 创建分析任务
- 文档解析
- 条款抽取
- 当事人、金额、日期、租期等实体抽取
- 风险规则匹配
- LLM 兜底判断
- 任务状态：待分析、分析中、已完成、失败
- SSE 或其他实时进度通道
- 进度 checklist：解析文档、抽取条款、匹配规则库
- 超时、取消、重试
- 失败原因与下一步操作

### E. 条款抽取与合同结构

这是风险报告和问答的事实基础，用户可以不直接看到完整 schema，但产品必须围绕它组织内容。

- 条款编号与标题
- 条款类型：租金、押金、违约金、租期、维修、续租、解约、转租等
- 条款原文
- 金额、月份、日期区间
- 责任主体
- 条款完整性与解析置信度
- 条款与风险的一对多关联
- 条款引用的稳定 ID

### F. 风险雷达报告

这是一期最重要的结果模块，必须能回答“哪里有问题、为什么、怎么处理”。

- 合同健康度分数及其解释
- 风险数量汇总：高 / 中 / 低
- 风险列表与排序
- 风险等级、标题、涉及条款号
- 风险原因与规则依据
- 修改建议
- 谈判话术
- 风险状态：未处理、已查看、已忽略或已解决（后续可选）
- 点击风险进入对应原文位置
- 报告加载、部分完成、空风险、分析失败状态
- 明确“建议而非法律意见”的产品边界

### G. 合同原文与条款定位

原型以右侧抽屉承载原文，这个模块是“风险可解释”的核心交互。

- 打开指定合同原文
- 展示合同基本信息与解析状态
- 按条款顺序阅读
- 风险条款高亮
- 风险条款标签与解释
- 从风险卡片跳转并滚动到指定条款
- 从问答引用点击跳转到指定条款
- 抽屉关闭、遮罩关闭、返回报告后保持上下文
- 原文加载失败、合同不存在、未完成分析时的状态
- 后续可扩展：条款目录、关键词搜索、复制原文、下载原文件

### H. 合同问答 Agent

对话不是泛聊天，而是围绕当前合同提供可追溯问答。

- 基于当前合同追问
- 无当前合同时转入租房知识问答
- 识别违约金、押金、续租、维修、退租、转租等主题
- 引用已存在的条款，不允许编造条号
- 引用条款可点击定位
- 流式回答与输入中状态
- 规则检索失败时的降级回答
- 当前合同绑定，不能静默切换到其他合同
- 追问时展示引用来源、建议和风险边界
- 对话历史消息持久化策略

### 租房领域能力 3：房源整理与建议

面向产品侧维护的房源库，也允许用户补充自己收集的房源信息。第一阶段不默认接入外部房源平台，而是先把房源数据的完整度、有效状态和可比较性做好。

- 房源数据维护：来源、更新时间、有效状态、区域、价格、费用和联系方式
- 房源状态：待核实、可看房、已失效、已签约、已放弃
- 单条房源信息录入
- 多条房源批量粘贴或附件导入
- 从非结构化内容提取房租、押金、面积、户型、楼层、朝向、位置、通勤、配套、费用、入住时间等字段
- 识别信息缺失、描述模糊和明显异常
- 按用户偏好筛选：预算、通勤、区域、面积、独立卫浴、采光、楼层等
- 计算总成本：月租、押金占用、中介费、物业费、网费和预计通勤成本
- 多房源横向比较
- 输出推荐理由、优点、缺点、风险、待确认问题和不推荐原因
- 给出“更适合谁”的解释，而不是只输出单一排名
- 允许用户继续追问某套房源
- 房源信息与附件、对话上下文、后续合同关联
- 外部链接解析、实时房源数据和价格趋势暂列后续能力

### I. 行动输出

让用户拿到结果后能立刻做下一步，而不是停留在“看过报告”。

- 一键复制谈判话术
- 复制成功反馈
- 导出风险报告
- 导出格式：PDF / Markdown / Word（待确认）
- 导出内容：合同摘要、风险清单、条款原文、修改建议、免责说明
- 分享报告或生成只读链接（后续能力，涉及权限）
- 下载原始合同

### J. 合同库

原型侧栏已出现“我的合同”，PRD 也将其列为后续阶段能力。它是多合同产品化的基础。

- 合同列表
- 合同名称、来源、创建时间、分析状态、健康度
- 打开合同原文与风险报告
- 对失败合同重新分析
- 对分析中合同查看进度
- 删除合同与二次确认
- 重命名合同
- 搜索、筛选、排序
- 合同归档
- 两份合同对比（Phase 1）

### K. 对话历史

原型有“最近对话”区域，但当前实现只是临时展示，因此需要单独定义数据生命周期。

- 会话列表
- 会话标题自动生成与手动重命名
- 打开历史会话
- 会话关联的合同
- 会话删除 / 清空
- 空态、加载态、分页或无限滚动
- 刷新后是否保留
- 多设备同步策略

### L. 租住辅助工具

这部分来自现有 PRD 的 Phase 1/Phase 2，不属于当前风险雷达主闭环。

- 租期、续租、押金退还等时间线
- 到期提醒与通知
- 看房 / 签约 / 退租 Checklist
- 房屋交接记录
- 维修记录与证据整理
- 多合同对比

### M. 知识与高级能力

这部分是产品愿景，但当前不能与一期能力混在一起。

- 知识图谱可视化
- 法规与规则来源浏览
- 纠纷模拟
- 合同模板库
- 房东坑点库
- 个人知识库
- 室友协作
- 订阅 / 付费 / 配额

### N. 系统、合规与运营支撑

- 用户协议、隐私政策、免责声明
- 反馈与问题上报
- 风险结论纠错 / 申诉
- 服务状态与模型状态
- 数据删除与导出
- 管理员规则库管理
- 模型调用、分析耗时、失败率和成本监控
- 真实合同评测集与规则回归

## 3. 建议的优先级

### P0：先做完整的对话 Agent 原型底座

工作台空态、三类租房场景入口、上下文展示、聊天记录、流式输出、暂停输出、附件上传、发送 / 失败 / 重试状态、连续追问和免责提示。

P0 原型需要同时演示三类租房任务，但不代表工程实现必须同时把三类能力做到同等深度：

- 租房知识问答：至少完成一个问题到可执行建议的对话链路。
- 合同理解：至少完成导入、分析、风险、原文定位和追问链路。
- 房源建议：至少完成多条房源整理、比较和建议链路。

### P1：围绕房源推荐主场景完成产品化

围绕房源库、推荐解释和房源—合同核验做深，同时补齐登录 / 注册、用户数据隔离、房源与会话持久化、附件持久化、合同库或房源记录、重命名与删除、分析失败重试、报告历史、隐私与数据删除。

### P2：提升租住决策效率

合同对比、时间线提醒、租住 Checklist、交接记录、报告分享、更多导出格式、跨对话记忆和用户偏好档案。

### P3：扩展产品边界与商业化

知识图谱可视化、纠纷模拟、模板库、房东坑点库、室友协作、订阅付费、运营后台、外部房源平台接入。

## 4. 原型页面 / 状态清单

先不按代码路由拆，而按用户可感知的页面和状态拆：

1. 登录页：验证码登录、密码登录、协议未勾选、验证码倒计时、登录失败、登录成功。
2. 工作台空态：首次进入、已有上下文、无当前会话、三类租房任务入口。
3. 普通问答态：输入问题、上下文补充、流式输出、暂停输出、继续追问、重新生成、回答失败。
4. 附件态：选择附件、上传中、上传成功、预览、移除、解析中、解析失败、附件进入上下文。
5. 合同输入态：粘贴文本、文件选择、格式校验、长度不足、上传失败、识别为合同。
6. 合同分析态：解析、抽取、规则匹配、超时、取消、重试。
7. 合同结果态：风险报告、无风险、部分风险、报告加载失败、谈判话术、导出。
8. 租房知识结果态：直接回答、需要补充信息、引用来源、风险提示、继续追问。
9. 房源建议态：房源批量输入、字段整理、缺失信息、横向比较、建议与待确认问题。
10. 原文 / 附件详情态：加载中、完整内容、定位高亮、关闭、内容不存在。
11. 合同库 / 房源记录态：列表、空列表、分析中、失败、已完成、删除确认。
12. 历史会话态：列表、空列表、打开、重命名、删除、持久化失败。
13. 账号与设置态：用户资料、套餐、退出、隐私与数据管理。
14. 导出与分享态：生成中、成功、失败、权限限制。

## 5. 当前必须先解决的产品矛盾

这些不是实现细节，而是会直接改变页面和数据模型的决策：

| 问题 | 原型 / 文档现状 | 建议先定的原则 |
|------|------------------|----------------|
| 产品主题与首个主场景 | 已确定产品标题和“房源推荐为主、合同审查与租房常识为辅”的方向 | 首页优先承载房源维护、比较和推荐；合同审查与常识问答围绕目标房源展开 |
| 上下文的边界 | 用户补充了基本上下文与聊天记录，但尚未区分单轮上下文、当前会话记忆和跨会话长期记忆 | P0 先做当前会话上下文；跨会话长期记忆放 P2，避免一开始引入不可控的记忆行为 |
| 暂停输出的语义 | 已确定需要暂停输出，但“暂停后能否继续同一答案”还未定义 | 建议 P0 的暂停是停止生成并保留已输出内容；继续操作通过新一轮追问或“重新生成”，不承诺从 token 位置恢复 |
| 附件如何影响对话 | 已确定有附件上传，但附件是否自动进入上下文、是否支持多个附件未定 | 上传成功后先展示附件卡片并标记“已加入当前对话”；允许用户移除，多个附件作为独立上下文项管理 |
| 房源建议的数据来源 | 以产品侧自维护房源库为主，同时允许用户补充候选房源；外部平台实时接入尚未确定 | 第一版先保证房源字段、来源、更新时间和有效状态可维护；外部平台解析、实时价格和地图数据后置 |
| 租房知识的可信来源 | 当前文档主要描述合同条款和规则，没有定义知识问答的来源 | 先区分常识 / 经验 / 法规政策；法规政策类回答必须带来源或明确提示需要核实 |
| 是否正式做登录 | 有独立登录原型；当前一期代码写明未做登录与数据隔离 | 如果保留登录页，就把账号、归属和隔离列入 P1；否则暂时从主原型移除，不宣称“仅自己可见” |
| 一期支持哪些输入 | 原型写 PDF / Word / 粘贴；一期方案明确 PDF + 粘贴，不做 OCR | 一期先锁定 PDF + 粘贴；Word 和图片分别明确为支持或延后，不留无行为按钮 |
| “知识图谱”是否是用户功能 | 品牌和文案大量出现图谱；一期方案不做 Neo4j 和图谱页面 | 一期把它定义为内部溯源概念，不做独立图谱页，避免用户期待与能力不一致 |
| 最近对话是否真实持久化 | 原型有入口；当前实现刷新即清空 | 若要保留入口，至少定义会话表、保存时机和删除规则 |
| 报告导出范围 | 原型有导出按钮，但只是演示 Toast | 先确定格式、内容、是否带原文、是否允许分享，再做页面状态 |
| 健康度分数如何解释 | 原型直接显示 78 / 100 | 需要定义评分公式、风险等级权重及“不是法律结论”的解释文案 |
| 登录方式是否全部实现 | 原型包含短信、密码、微信、支付宝、Apple | 一期建议只选一种主登录方式，其余显示为规划项，避免做出多套空壳流程 |

## 6. 下一步原型顺序

建议按以下顺序逐页确认，而不是马上继续写 React：

1. 先固化房源推荐主流程：维护房源、设置偏好、筛选比较、解释推荐理由、记录待确认事项。
2. 固化 Agent 交互规范：上下文、聊天记录、流式输出、暂停输出、附件上传、失败重试。
3. 补一张“从选房到签约”的用户主流程图，明确房源、合同和常识问答如何共享上下文。
4. 完善工作台核心状态：房源录入、推荐结果、合同核验、普通问答、附件上传、暂停输出、连续追问。
5. 再做合同原文、房源详情、合同库 / 房源库、历史会话和账号设置的延伸原型。
6. 所有页面状态确认后，再把原型拆成前端组件和后端 API。
